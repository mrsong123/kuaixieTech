# 商品保险：保险机构定价、直收与保单核验

收付规则已确认：客户自主投保，保险机构定价并直接收费，平台不代收或托管保险费。此规则替代此前保费随下单托管的安排。真实保险机构 API 接通、数据库迁移和实际资金操作尚未执行。

保险采用独立保险合同边界。客户在购买商品时自行选择保险机构与险种，或选择本次不购买保险。平台提供交易及投保协助，不以平台资金担保、垫赔或承诺兜底；依法应承担的交易、信息披露及服务责任仍须履行。实际条款、销售资格与披露文本需按合作合同核定。

## 当前真实状态

已列出 12 家常见财产保险机构，均为参考名单，不表示合作、产品可售或 API 已接通。当前没有注册真实保险机构适配器，没有配置商户凭据，没有真实报价、投保、出单、退保或理赔调用。所有实际投保默认关闭。不能仅填写 API Key 就把未实现的承保协议变成可用服务。

运营后台设置页新增保险产品管理及投保记录，前台订单表单新增机构/险种选择，五端业务目录新增投保与保单中心。产品按适配器明确声明的 web、h5、app、mp_weixin 能力分别开放，不默认假设保险机构页面支持所有终端；直付页面与报价终端绑定。产品必须完成机构独立协议适配、签名与验签、资质/产品能力核验及联调，且密钥就绪后才允许启用。参考名单并不限制增加其他合法承保机构。

## 交易与保险资金分开

新订单计价版本为 `escrow_v2_external_insurance`：货款、5% 服务费进入交易托管，带货人履约保证金仍为货值 20%。平台保费为 0；不再按货值 1%、最低 5 元收取平台保价费。真实保费采用客户选定保险产品的有效机构报价，并由客户直接向保险机构支付，不进入钱包、佣金、平台收入或风险池。

原 `escrow_v1` 及更早订单保留其计价快照，历史托管资金不能自动改写。对尚未完成、含非零历史保价费的订单，自动扣收和结算暂停，先核对实际承保与费用去向；已完成记录不改写。历史费用记录不构成保险出单证明，须单独核对承保机构、保单、保费去向及退款责任。新的外部保险状态不会追认历史订单已承保。

买家订单取消和保险退保属于不同合同流程。交易退款不会自动冒充保险机构退还保费；退保、理赔由客户在机构服务入口办理，或待该机构正式 API 实现并联调后再开放相应操作。当前没有通用的自动退保或理赔赔款 API。

## 报价和投保流程

1. 客户明确选择是否购买保险。选购时，选择实际已连接的保险产品，并读取条款、免责和承保限制。
2. 后端向该机构的原生适配器请求报价，绑定本人、行程/竞价报价/既有订单、商品名称、申报货值、产品版本、条款版本与有效期。无有效机构报价不得确认“选购保险”的新订单。
3. 交易下单仍只托管交易款。订单 `insured` 保持 `unselected`，选择意向和保险报价引用保存在订单快照中。
4. 买家再次确认产品条款、必要资料提供与机构直付。后端锁定本人订单和报价，幂等保存申请及同意记录。
5. 机构适配器收到真实订单风险资料；额外身份、健康、运输或合规资料依产品要求由机构核保页面采集。适配器必须验证最终风险范围、保费和条款与锁定报价相符后返回收银台。
6. 客户在机构页面完成核保及付款。创建申请、打开付款页、客户端返回成功均不代表承保。
7. 后端主动查询机构，适配器先按官方协议认证响应/验签，再校验平台申请引用、机构申请号、订单、实际承保机构、产品代码、申报货值、保费及币种、条款版本和直接付款结果。
8. 完整、已核验的保单号、独立保障引用、保险凭证和保障起止时间匹配后，才更新承保状态。未来生效显示 scheduled，已过期显示 expired；失败和待核保均不标记已承保。

在提交投保前，客户可以针对原订单重新选择产品、获取新报价并重新同意条款，不改变交易托管金额。申请一旦已提交或结果不确定，保持原申请引用，禁止静默重发、换保险机构或创建第二份扣款。已提交申请的改保、重投须依机构撤销及幂等协议实现，目前不自动处理。

选择购买保险的 v2 订单，在采购和发货确认时检查该单保单已生效、尚未到期、最近 5 分钟内核验成功且没有未确认错误。状态不满足则拒绝继续确认，客户可在保单中心主动核验。未选保险的订单不制造保单，也不触发此检查。

## 金额、资料与权限

交易申报货值使用 CNY 精确小数。保费可使用机构实际支持的 ISO 币种与最小单位，接口传十进制字符串，后端不使用浮点计算。保险保费和平台钱包换算相互独立，不伪造保险机构汇率。

保险产品保存凭据组/环境前缀；原生适配器可通过 IntegrationCredentials 读取 API 配置中心的加密凭据或环境引用，各机构后缀仍须按其真实协议实现。不得在产品名称、备注、日志或普通 JSON 中保存明文密钥；密钥仅在专门的受保护配置表单录入，不回显。当前仍无保险机构原生适配器，不因存在凭据组就宣称已接通。

接口身份来自会话；买家仅查询和提交自己的订单、报价、申请、凭证及同意记录。后台仅管理员可配置产品及查看申请记录。申请同意使用现有 `t_consent_records`，记录条款版本、资料提供说明版本、接收机构、目的、资料类别及权利渠道，不额外复制收货人实际资料到同意记录。

原生适配器应使用 `InsuranceHttp`：HTTPS、正常 CA 与会话代理、禁止跳转、最长 30 秒请求时限。出站主机同时受到产品 serviceHosts、环境 `INSURANCE_API_ALLOWED_HOSTS` 与云环境网络策略约束。证书、条款、理赔及收银台各自检查精确主机，不允许调用方提交任意外链。不得禁用 TLS 或假定所有机构使用同一种签名。

## 原生适配器验收要求

`InsuranceModels.Adapter` 定义 quote、apply、query 边界。每家机构实现独立适配器，固定声明 insurerCode。真实接入至少需要：

- 正式机构、销售/服务合同、产品代码、可承保货物、路线、地区、币种及资料要求。
- 官方 API 文档、测试与生产端点、应用/商户标识、密钥或证书、签名及响应验签规则。
- 报价有效期、核保补件、申请幂等、真实直付、查询一致性及保单生效语义。
- 真实产品条款、免责、退保和理赔服务入口，以及凭证的身份与下载授权要求。
- 网络超时后的查询恢复、重复/延迟响应、政策变更、取消、到期及凭据轮换验证。

没有通用的虚构保险 HTTP 协议，也没有预置假保费或假保单。运营不能直接修改数据库或点击“审核通过”把申请设成有效保险。只有已认证机构响应才可改变承保结果。

## 数据库方案

`003-goods-insurance.proposed.sql` 提议新增产品、不可变报价和投保申请三表；未执行。现有 `t_consent_records` 用于实际同意记录。原 `t_store_insurance_policies`、`t_insurance_coverages` 描述店铺保单及关联保障，不能把个人新投保凭证冒充店铺保单写入；`t_risk_pool` 不用于新商品保险垫赔。

全部增量共 18 张提议表，含基准 SQL 共 100 表、1063 字段，完整闭环仍待逐字段验收。真实数据库连接、迁移审阅与执行、并发和机构联调尚未完成。

## 运行与回执恢复

客户可主动查单。可通过 `app.insurance.reconcile-enabled=true` 开启定时查询，每批最多 100 笔并按上次检查时间轮转；默认关闭。网络结果不确定保持 dispatching，不重复投保。查询失败记入脱敏错误且不确认为生效。历史凭证有独立只读接口，机构查询临时失败时仍可读取已存的保险凭证引用。

目前不提供未经机构协议定义的匿名回调入口。后续每家机构的回调应先认证，再触发官方主动查询或等价的经过验证流程，禁止信任客户端提供的支付/承保状态。

## 本轮验证

当前应用 89 项后端测试、17 项共享业务断言、SDK 契约、21 个原有流程、国际化运行时（含 JPY/BHD 精度）和移动端完整类型检查已执行。PC、后台、H5、小程序和 App 资源构建已执行。均不代替真实机构 API、真实库、并发及真机验收。默认 Maven 历史测试、旧视觉检查和缺失迁移清单的问题仍单独保留。

保险报价与保障时间按 UTC 瞬时处理。真实部署前须核验 JDBC 连接与数据库会话的时区，以及历史 DATETIME 的存储口径；不能直接把存量本地时间当作 UTC，也不能未经核对切换会话时区。
