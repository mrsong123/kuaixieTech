# 原充值单原路退款

该功能退回本人已核验的原充值付款，**不是商品售后退款**。不将任一商品争议金额随意退到某次充值渠道；商品货款售后、退款费用来源归因、银行卡提现及跨币种退款仍需单独实现。

当前支持有已核验收款回执的 CNY 微信/支付宝充值单全额退回。原支付保持 paid，表示历史确已收到并入账；不改成可再次充值入账状态。原支付额与原钱包入账额可能因历史费用或价差不同，均独立精确匹配源回执：钱包预留扣 base_minor，原路退款退 payment_minor。

1. 本人申请：锁原支付单，校验交易/商户/币种/金额/精度及源收款回执；可用钱包足额才原子扣出预留，写申请和审计事件。
2. 管理员审核：审核通过只变 approved，不自动出款；驳回或本人在 requested 撤回，会原子释放预留。
3. 明确派发：先校验原商户快照和本地密钥、试签及请求约束，再单独事务提交 dispatching 的执行归属；提交后才调用支付机构。
4. 查询结果：签名回执必须匹配退款号、原支付号、原交易号、币种、原总额及退款额。真实成功才显示 succeeded；未知结果只允许查询，不再次派发。

微信使用 APIv3 原交易退款及查询，成功/关闭/处理中状态严格映射，理由规范化到公开接口限制内。支付宝使用 RSA2 原交易退款及 fastpay.refund.query，核对签名及公开 REFUND_SUCCESS；无成功状态不推定到账。渠道受理和服务端记录成功也不承诺银行到账时刻。

一笔原支付由唯一 active_slot 控制预算。只有 cancelled/rejected、dispatched_at 为空且钱包预留已释放的历史申请才不占活跃位，允许新的请求键重新申请；旧申请和事件均保留，原键重试返回原记录。已派发、长期未决、成功以及渠道关闭记录不自动放开预算，必须由运营核对原渠道，不能用重试绕过重复退款保护。

派发后网络不确定会保留预留与未决状态，不自动返钱包、不自动再次退款。渠道明确 closed 时释放钱包但保留已派发历史预算保护。终态重放不重复释放或出款。受保护的事件分页出口供本人和管理员查看时间线，不返回内部 actor_id、原商户快照或密钥。

前台“原充值单退款”和后台交易管理均已接入；审核、派发、查询、撤回为独立明确动作。未决操作不盲目重复。会话变化后阻止旧确认、旧请求及其后续请求使用新账号，原生页栈与 PC 业务界面同时处理账号切换。

本轮修复了原充值收款回执 INSERT 缺失 payment_minor_digits 必填字段，并限制账务 kind 长度适配原库 VARCHAR(16)。新退款账务类型为 refund_reserve/refund_release，原提成入账/撤销的超长类型也改为不超过16字，不重写历史账务记录或改变分佣费率。

007 仅新增 t_payment_refunds 和 t_payment_refund_events，两表均未执行。没有调用真实退款或修改业务库。当前不包含支付机构退款通知推送、自动长期对账/告警、跨币种退款、银行卡网关退款或提现；操作员只能通过已有查询得到实际结果，不能伪造成功。
