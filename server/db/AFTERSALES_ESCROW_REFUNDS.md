# 商品售后托管钱包退款

本模块只处理能够逐项证明尚未结算的商品货款托管。退款到账位置为购买人的平台钱包（`escrow_wallet`），不表示微信、支付宝或银行卡原路到账。原充值退款使用独立的 payment-refunds 流程，二者不互相调用。

## 资金证明与执行

仅支持人民币商品订单、已消耗库存的商品预留、外部保险新版计价、购买/发货状态、未结算订单。原订单、商品预留、唯一冻结 buyer_escrow、冻结流水、既往售后退款及其来源链必须一致。存在历史保险扣费、退税补偿计划、已发奖励、其他参与方正向出款、来源漂移或不明金额时拒绝执行并要求对账。

管理员先读取预算，再按当前裁决轮次提交唯一 UUID 确认。预算查询不修改资金。执行在事务内锁定订单与案件，校验裁决和来源，真实增加购买人钱包，同时等额减少订单 buyer_deposit 与冻结保证金行 amount。余额流水、不可变来源记录、审计事件和案件状态同时落库；任一失败整体回滚。相同请求重试返回既有结果，不重复入账。不得通过修改数据库记录绕过待核对状态。

## 部分退款与全额货款退款

部分退款后，商品原始 goods_amount 保持历史事实，后续带货人货款结算使用扣除已退金额后的净额。存在售后退款时，不自动按原总额发放新的首单奖励、团队提成或刷新层级，等待运营确认业务标准。

累计退完货款后，退款本身已经到账，但案件保留 awaiting_accounting。服务费、运费、带货人保证金及其他费用的归属仍需人工核对，模块不会推断新费率、自动返库存或自动分配这些资金。全额待核对订单不应继续自动结算。取消订单只退订单和保证金行中剩余托管金额，终结冻结保证金台账；部分罚没状态使用 VARCHAR(16) 可容纳的 partial_forfeit。

净额结算再次校验当前订单和不可变退款来源；若当前订单已有退款标记但查询不到历史，拒绝按原额付款。历史来源缺失和长期待核对不能通过自动释放预算解决。

## 接口与审计出口

- 管理员：GET `/api/portal/admin/after-sales/{caseId}/escrow-budget`，POST 同路径 `/escrow-refund`。请求包含 requestId、expectedRound、note。
- 本人：GET `/api/me/after-sales/escrow-refunds`，仅返回本人退款记录。
- 本人/管理员：各自命名空间 `/after-sales/escrow-refunds/{id}/events`，只读分页事件。
- 案件详情存在退款时返回 refund_method=escrow_wallet 和 escrowRefund，明确平台钱包去向。

事件和记录不能编辑，展示数据不暴露操作者标识、内部来源快照或商户凭据。迁移为 `009-order-escrow-refunds.proposed.sql`；最终部署由汇总 SQL 统一执行，本次未连接业务库或调用真实资金渠道。

## 验证范围

单元测试覆盖来源证明、并发比较更新、重复请求、部分/累计全额退款、资金双减、净额结算、奖励抑制、剩余托管取消和保证金终态。模拟测试不代替实际 MySQL 事务/锁、迁移及业务库联调验收。
