# 跨端统一与数据库闭环执行记录

用户要求：先统一小程序、Android、iOS、PC 与 Web 的展示和功能，再完成后台、前台、Spring Boot 与所有现有表和字段的业务闭环。

本记录追踪实际实现，不把导航入口、实体类、SQL 引用或编译成功当作业务已经闭环。当前任务尚未全部完成。

## 已实施的统一

- 五端主业务目录统一为广场、社区、发布、消息、我的，定义在 SDK 的 businessNavigation.ts。
- PC 首页改为行程/求购广场；PC 与移动端使用同一地区、方向、搜索和品类国家关联过滤规则。保留原商品目录、行程详情与意向下单入口。
- PC 社区读取真实求购与动态接口，替换旧规划占位。PC 发布页使用与移动端相同的发布业务模型。
- 登录、注册、验证码发送、找回密码使用相同业务模型；移除 PC 普通登录中的手工令牌输入。微信原生登录仍由平台适配器提供；PC 未冒充已接通微信网页扫码登录。
- 21 个原有认证、账户安全、报价、履约与通信流程统一业务目录及执行模型，现覆盖 50 个核心用户操作。接单保证金由后端订单读取并明确确认，不由用户任意填写；邀请流程补接加入申请匹配。PC 新增正式业务表单入口，不再将普通用户引导到 API 工具台。报价、保价选择、确认金额和危险操作确认共用规则。
- PC 新增本人订单、求购、行程、通知、资料、钱包和客服入口。移动端“我的商品”改接真实商品管理。
- 地址簿、收藏和购物车补齐后端接口，PC 和移动端共用读写模型；从商品详情可加入收藏或购物车，从收藏/购物车可回到商品详情。
- 地址全部字段参与本人地址管理，默认地址按所属账号串行更新；意向下单可选择已保存地址并再次核对。旧订单地址快照不会跟随地址簿变更。
- 商品详情改为按 ID 查询，摆脱首批 100 条目录的限制；隐藏、下架、无库存及卖家不符合要求的商品不可公开查询。

上述实现仍需真实库与真机验收。购物车不扣款、不锁库存；批量购物车结账尚未完成；单商品选卖家普通行程、库存预占与托管成单已在本轮实现，仍未真实库验收，不会显示假支付成功。

## 全表、全字段验收

`server/db/business/domains.json` 对原始 82 表和提议新增 23 表分配业务责任域及前后台目标用途。`docs/DATABASE_BUSINESS_COVERAGE.csv` 与后台“业务与字段验收”页逐字段列出说明、目标用途、候选 SQL 文件和验收状态。

当前共 105 表、1122 字段。完整验收回执尚未建立，全部保持 pending。这不代表已写代码没有作用，而是尚未具备“前台业务、后台操作、后端逻辑和测试全部可核验”的逐字段证据。候选引用只能辅助查找代码。

后台字段验收页受管理员权限保护，只返回交付元数据，不读取或返回业务数据、密钥、证件或验证码内容。它是缺口追踪入口，不能代替表对应的真实业务功能。

完整性检查：

```sh
python3 server/tools/audit_business_coverage.py
python3 server/tools/audit_business_coverage.py --require-complete
```

第二条当前应返回非零。没有完整回执就不能报告全部交付。回执放在 `server/db/business/acceptance.json`，按 table.column 指定 frontend、admin、backend、test 的实际文件以及 result=passed；工具校验文件存在，运行时与业务语义仍须人工验收。新增表若没有业务责任映射会报错。

## 真实环境条件

当前云实例未注入 DB_URL、DB_USER、DB_PASSWORD、APP_JWT_SECRET，也没有支付商户凭据。未向业务库执行迁移、未触发真实支付或其他资金操作。需要先落实连接和服务配置，才能核验真实结构并按此前约定审阅迁移。密钥只通过环境设置配置。
